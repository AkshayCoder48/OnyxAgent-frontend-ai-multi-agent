**Diagnosed from:** OnyxAgent web app (`onyxagent-lac.vercel.app`) — live tests run against the deployed API on 2026-09-03.
**Goal:** fix the three problems the web app hits: the intermittent **HTTP 502 "edge runtime does not support Node.js 'crypto' module"**, the **"AI says it has no tools"** behavior on several models, and make tool-calling work identically from every client.

## 2. FIX A — the 502 `upstream_error` "The edge runtime does not support Node.js 'crypto' module"

The exact failure the app saw (wrapped by your gateway):

```json
{"error":{"message":"The edge runtime does not support Node.js 'crypto' module.\nLearn More: https://nextjs.org/docs/messages/node-module-in-edge-runtime","type":"upstream_error","param":null,"code":"upstream_error"}}
```

That message is generated by **Vercel/Next.js when an Edge-runtime function imports `node:crypto`**. Since your error envelope types it `upstream_error`, one of two things is true:

1. **One of your provider adapters calls an upstream that is itself a Vercel Next.js app running on the Edge runtime with a `node:crypto` import** (the error text is the upstream's response body), or
2. **Your own gateway route is Edge runtime** and imports something that pulls in `node:crypto` (e.g. `createHash`, `randomUUID` from `node:crypto`, or a transitive dep like a JWT/signing library) — and your error handler wraps its own crash as `upstream_error`.

### How to find it in your repo

```bash
# Any route explicitly on the Edge runtime?
grep -rn "runtime.*=.*['\"]edge['\"]" app/ pages/ src/

# Any node:crypto usage (direct or via imports)?
grep -rn "node:crypto\|from ['\"]crypto['\"]" app/ pages/ src/ lib/
```

Check the **Vercel deployment logs** for the 502 around the time it fired — the function name in the log line is the culprit route.

### Fix (pick one)

**Option 1 — move the route to the Node.js runtime** (simplest, recommended):

```ts
// app/api/v1/chat/completions/route.ts (and any other affected route)
export const runtime = "nodejs";        // ← was "edge" (or unset while an edge config applied)
export const maxDuration = 60;          // Node functions can stream long responses
```

If you set edge via `next.config.js` (`experimental.runtime: 'edge'`), remove that and set per-route `runtime` instead.

**Option 2 — keep Edge, port to Web Crypto** (Edge-compatible):

```ts
// ❌ Edge-unsupported
import { createHash, randomUUID } from "node:crypto";
const id = randomUUID();
const sig = createHash("sha256").update(body).digest("hex");

// ✅ Edge-supported (WebCrypto is global in Edge)
const id = crypto.randomUUID();
const sig = Buffer.from(
  await crypto.subtle.digest("SHA-256", new TextEncoder().encode(body))
).toString("hex");
```

> Web Crypto is async; anywhere you hashed synchronously needs to become `await`.

### Also: don't let a transient upstream 5xx kill the client's whole turn

Wrap the upstream call with 1–2 retries and, ideally, failover to another provider serving the same model family:

```ts
async function fetchUpstreamWithRetry(url: string, init: RequestInit, attempts = 3) {
  let lastErr: unknown;
  for (let i = 0; i < attempts; i++) {
    try {
      const res = await fetch(url, init);
      // Retry only gateway-ish failures — never 4xx (client's fault).
      if (res.status >= 500 || res.status === 429) {
        lastErr = new Error(`upstream ${res.status}`);
        await new Promise(r => setTimeout(r, 1500 * (i + 1)));
        continue;
      }
      return res;
    } catch (e) {
      lastErr = e;
      await new Promise(r => setTimeout(r, 1500 * (i + 1)));
    }
  }
  throw lastErr;
}
```

## 3. FIX B — "the AI says it has no tools" (tool calls hidden in the TEXT)

This is the big one for the web app. Several of your upstreams **cannot emit the standard `delta.tool_calls` SSE chunks**. Instead the model writes the tool call as a **fenced code block inside `delta.content`**:

`tb/gpt-4o-latest` and `ua/chat-model-reasoning` (verified live, streaming, tools + tool_choice auto):

```
data: {"choices":[{"delta":{"content":"```tool_call\n[{\"name\":\"get_weather\",\"arguments\":{\"city\":\"Tokyo\"}}]\n```"}" ...
data: {"choices":[{"delta":{},"finish_reason":"stop"}]}    ← note: "stop", NOT "tool_calls"
data: [DONE]
```

Zero `delta.tool_calls` chunks — `grep -c "tool_calls"` on the stream = 0. A standard OpenAI client (like the app) therefore sees **plain text**, renders it as a code block, never executes the tool, and the model — receiving no tool result — concludes "I don't have tools". Your docs promise `assertToolsForwarded (nothing dropped)` — the *request* tools ARE forwarded, but the *response* tool call never makes it into the standard field.

### The fix: normalize text-embedded tool calls into standard chunks in your streaming parser

Detection regex (works for `tool_call`, `tool_calls`, `tool-call`, `function_call` variants):

```ts
const FENCE_OPEN = /```(?:tool_calls?|tool-calls?|function[_\s-]*calls?)\s*\n?/i;
const FENCE_FULL = /```(?:tool_calls?|tool-calls?|function[_\s-]*calls?)\s*\n?([\s\S]*?)```/gi;
```

**Streaming path** — in your SSE re-emitter:

1. Accumulate `delta.content` per message as usual.
2. When the accumulated text matches `FENCE_OPEN`, **stop forwarding those text deltas** to the client (buffer them).
3. When the fence closes (or the stream ends), parse the body:

```ts
function parseFenceBody(body: string) {
  const parsed = JSON.parse(body.trim());                 // array OR single object
  const arr = Array.isArray(parsed) ? parsed : [parsed];
  return arr.map((it, index) => ({
    index,
    id: `call_${Date.now()}_${index}`,                    // stable id for the tool result round-trip
    type: "function",
    function: {
      name: it.name ?? it.function?.name,
      arguments:
        typeof (it.arguments ?? it.function?.arguments) === "string"
          ? it.arguments ?? it.function?.arguments
          : JSON.stringify(it.arguments ?? it.function?.arguments ?? {}),
    },
  }));
}
```

4. Re-emit as **standard chunks** so every OpenAI client just works:

```
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"name":"get_weather"}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\"city\":\"Tokyo\"}"}}]}}]}
data: {"choices":[{"delta":{},"finish_reason":"tool_calls"}]}     ← "stop" → "tool_calls"
```

5. Any text that preceded the fence stays as normal content deltas; the fence body itself is never shown as text.

**Non-streaming path** — in the JSON response builder, apply the same transform to `choices[0].message`:

```ts
function normalizeMessage(message) {
  let toolCalls = message.tool_calls ?? [];
  let content = message.content ?? "";
  if (toolCalls.length === 0 && typeof content === "string") {
    const m = [...content.matchAll(FENCE_FULL)];
    const open = FENCE_OPEN.exec(content);
    if (m.length || open) {
      const body = m.length ? m.map(x => x[1]).join("\n") : content.slice(open.index + open[0].length);
      const calls = parseFenceBody(body);                // guard with try/catch — malformed JSON → keep as text
      if (calls.length) {
        toolCalls = calls;
        content = m.length
          ? content.replace(FENCE_FULL, "").trim()       // strip the block(s) from visible text
          : content.slice(0, open.index).trim();
        // finish_reason "stop" → "tool_calls" on the choice, too
      }
    }
  }
  return { ...message, content, tool_calls: toolCalls };
}
```

Also handle the **DeepSeek-style DSML tags** some free upstreams use (`<｜｜DSML｜｜tool_calls><｜｜DSML｜｜invoke name="...">`) the same way — parse `invoke` + `parameter` tags into `tool_calls` and strip the tags from content.

### Capability gate honesty

If an upstream genuinely can't call tools (e.g. `fx/chatgpt` answered "I don't have [access to call functions]" — verified live), **say so at request time** instead of accepting the request and dropping the calls:

```json
{"error":{"type":"tools_unsupported","message":"Model fx/chatgpt does not support client tools. Use a kc/* or l7/* model for tool calling.","code":"tools_unsupported"}}
```

…and tag the capability in `GET /api/v1/models` (e.g. `"capabilities": ["tools", "streaming"]`) so clients can filter. Right now a client cannot tell which of the 75 models actually round-trip tools.

## 4. FIX C — `/v1` compatibility aliases

Most OpenAI SDKs default to `{baseURL}/chat/completions` where `baseURL` conventionally ends in `/v1` (or they hit `{baseURL}/v1/chat/completions` when given a bare domain). Today those paths 404 with an **HTML page** (verified: `/v1/chat/completions`, `/chat/completions`, `/v1/models` → 404 `text/html`), which is painful to debug from an app. Add rewrites in `next.config.js`:

```js
module.exports = {
  async rewrites() {
    return [
      { source: "/v1/chat/completions", destination: "/api/v1/chat/completions" },
      { source: "/v1/models", destination: "/api/v1/models" },
      { source: "/chat/completions", destination: "/api/v1/chat/completions" },
      { source: "/models", destination: "/api/v1/models" },
    ];
  },
};
```

Then **any** base URL works: `https://freeaixyz4all.vercel.app`, `…/v1`, `…/api/v1` — all hit the same handlers. (Bonus: update the docs' "Base URL" row to mention all three.)
